# Featy 5분 발표자료 제작 가이드

> 이 문서는 PPT/Google Slides 제작자가 그대로 활용할 수 있도록 **슬라이드에 보일 문구**, **추천 레이아웃**, **발표 대본**, **평가 항목 대응**, **데모 체크리스트**를 분리해 정리한 자료다. 화면에 보일 문구는 짧게 유지하고, 세부 설명은 발표 대본에서 전달한다.

## 0. 발표 전체 전략

### 발표의 한 문장 목표

발표가 끝났을 때 심사위원은 다음을 이해해야 한다.

> **Featy는 빈 시간을 찾아주는 캘린더가 아니라, 팀의 맥락을 이해하고 실제로 성사될 회의 시간을 조율하는 AI 에이전트다.**

### 핵심 질문

- 기존 캘린더가 있는데 왜 또 필요한가?
- 단순 알고리즘이 아니라 왜 AI가 필요한가?
- AI가 사람 일정을 마음대로 결정하지 않는가?
- 4명이 3시간 안에 만든 프로토타입이 실제로 작동하는가?
- Skill과 Plugin은 장식이 아니라 실제 흐름에 사용되었는가?

### 권장 구성과 시간

| 구간 | 시간 | 역할 |
| --- | ---: | --- |
| 슬라이드 1 | 50초 | 문제와 사용자 가치 정의 |
| 슬라이드 2 | 70초 | Goal·Behavior·Context·Action·AI Tool 설명 |
| 슬라이드 3 | 70초 | 조율 로직과 AI의 필요성·안전성 설명 |
| 슬라이드 4 + 데모 | 120초 | 실제 작동 화면, Skill/Plugin, 결과 증명 |
| 마무리 | 10초 | 장기 비전과 한 문장 회수 |

총 4장 구성이 가장 안정적이다. 시연 영상을 별도 슬라이드로 쓸 경우 3번과 4번을 합쳐 4장 구성을 유지한다.

### 발표 내내 반복할 대비 문장

```text
기존 캘린더: 언제 비어 있는가?
Featy: 이 팀은 언제 만나야 하는가?
```

이 대비가 문제 정의, AI 필요성, 차별성, 장기 비전을 하나로 연결한다.

# 슬라이드 1. 빈 시간은 보여도, 최선의 회의는 결정되지 않는다

## 이 슬라이드의 역할

첫 50초 안에 문제와 사용자를 구체화한다. 기능을 먼저 설명하지 않고, 여러 사람의 일정을 맞출 때 생기는 **의사결정 문제**를 보여준다.

## 화면에 넣을 제목

> **빈 시간은 보여도, 최선의 회의는 결정되지 않습니다**

## 화면에 넣을 핵심 문구

왼쪽에는 기존 상황을, 오른쪽에는 Featy가 해결하는 질문을 배치한다.

### 왼쪽: 기존 캘린더가 알려주는 것

```text
누가 언제 Busy인가?
모두 겹치는 빈 시간이 있는가?
```

### 오른쪽: 팀이 실제로 결정해야 하는 것

```text
누가 반드시 참석해야 하는가?
누구의 일정은 조정 가능한가?
전원 참석이 안 되면 어떤 대안이 공정한가?
```

### 하단 한 문장

> **Featy는 캘린더 위에 올라가는 AI 일정 조율 레이어입니다.**

## Behavior · Context를 자연스럽게 포함하는 방법

- **Behavior:** 여러 사람의 캘린더를 열고, 단체 채팅에서 가능한 시간을 반복해서 물어보며, 결국 누군가가 수동으로 타협안을 정한다.
- **Context:** 해커톤·스터디·프로젝트 팀처럼 3~10명이 반복적으로 만나며, 멤버마다 중요도·선호 시간·출석 이력이 다르다.

이 두 용어를 슬라이드에 큰 표로 억지로 넣기보다, 실제 사용자 행동과 상황으로 보여준다.

## 추천 시각 구성

- 화면 왼쪽 45%: 여러 색의 캘린더 블록이 겹쳐 있지만 결론이 없는 모습
- 화면 오른쪽 45%: `전원 가능`, `조정 필요`, `대안 후보` 세 갈래가 나오는 간단한 흐름
- 중앙 또는 하단: “When is everyone free?” → “When should this team meet?”

복잡한 UI 카드 여러 개를 넣지 않는다. 하나의 대비 구도를 사용한다.

## 발표 대본 예시

> “팀 일정을 잡을 때 문제는 빈 시간을 못 찾는 것이 아닙니다. Google Calendar는 누가 언제 바쁜지는 보여주지만, 누가 꼭 참석해야 하는지, 어떤 일정은 조정 가능한지, 전원이 안 될 때 어떤 선택이 공정한지는 결정해 주지 않습니다. 결국 한 사람이 캘린더와 단체 채팅을 오가며 조율합니다. 저희는 이 의사결정을 자동화하는 AI 일정 조율 에이전트 Featy를 만들었습니다.”

## 다음 장으로 넘어가는 문장

> “그렇다면 Featy는 사용자를 대신해 정확히 무엇을 보고, 어떻게 행동할까요?”

# 슬라이드 2. 팀의 맥락을 읽고, 확정 가능한 행동까지 연결한다

## 이 슬라이드의 역할

평가에서 요구하는 `Goal / Behavior / Context / Action / AI Tool`을 한 흐름으로 설명한다. 다섯 개의 독립 정의가 아니라 **원인과 결과가 이어지는 에이전트 구조**로 보여준다.

## 화면에 넣을 제목

> **팀의 맥락을 읽고, 확정 가능한 행동까지 연결합니다**

## 화면에 넣을 핵심 구조

가로 방향의 단일 흐름을 권장한다.

```text
BEHAVIOR
캘린더와 채팅을 오가며 수동 조율
       ↓
CONTEXT
Busy/Free · 필수 참석자 · 선호 시간 · 출석률 · 회의 방식
       ↓
AI DECISION
자연어 조건 해석 · 후보 비교 · 타협 이유 설명
       ↓
ACTION
후보 제안 · 조정 요청 메일 · 사용자 확인 · 일정 확정
       ↓
GOAL
가장 많은 사람이 실제로 참석하는 회의
```

### AI Tool 하단 표기

```text
Rule Engine + OpenAI Responses API + Google Workspace Skills
```

## 다섯 요소의 정확한 정의

### Goal

단순히 공통 빈 시간을 찾는 것이 아니라, **필수 참석자를 지키면서 실제 참석 가능성이 높은 회의를 확정하는 것**이다.

### Behavior

사용자는 여러 캘린더와 메신저를 확인하고, 가능한 시간을 묻고, 불참자를 다시 설득하고, 확정 내용을 개별 통보한다. 반복적이고 맥락 의존적인 행동이다.

### Context

Featy가 판단에 사용하는 정보다.

- 개인별 Busy/Free 블록
- 필수 참석자 여부
- 개인별 그룹 중요도
- 그룹이 선호하는 요일과 시간대
- 대면·비대면·혼합 회의 방식
- 회의 길이와 중요도
- 최근 출석률과 하루 회의 부하
- 사용자가 직접 표시한 일정 조정 가능 여부

### Action

AI가 실제 업무 흐름에서 수행하거나 지원하는 행동이다.

- 가능한 슬롯 생성
- Top 3 후보 점수화
- 추천 이유 설명
- 충돌 멤버에게 개인화된 조정 요청 메일 초안 생성
- 사용자 승인 후 Gmail 초안 저장 또는 발송
- 최종 확인 후 캘린더 일정 생성

### AI Tool

- **Rule Engine:** 후보 생성과 점수 계산. 동일 입력에는 동일 결과를 내므로 안정적이다.
- **OpenAI Responses API:** 자연어 회의 요청을 구조화하고, 이미 계산된 후보의 이유와 타협안을 설명한다.
- **`gws-gmail-send` Skill:** 충돌 멤버에게 보낼 조정 요청을 Gmail 초안 또는 메일로 연결한다.
- **Google Calendar Skill/API:** 개인 일정 내용 대신 필요한 Busy/Free 범위만 읽는 방향으로 확장한다.

## 왜 Rule Engine과 AI를 나누는가

```text
계산은 규칙으로, 해석과 중재는 AI로.
```

이 문장을 반드시 강조한다. LLM이 존재하지 않는 시간이나 점수를 만들어내는 위험을 줄이고, 추천 결과를 설명 가능하게 만든다.

## 발표 대본 예시

> “Featy의 목표는 빈칸 하나를 찾는 것이 아니라 실제로 성사될 회의를 만드는 것입니다. 캘린더의 Busy/Free뿐 아니라 필수 참석자, 그룹 선호 시간, 출석률, 회의 방식 같은 맥락을 함께 봅니다. 후보 시간과 점수는 규칙 엔진이 안정적으로 계산하고, AI는 ‘이번 주 오후에 한 시간 잡아줘’ 같은 요청을 구조화하며, 전원이 안 될 때 누구에게 어떤 대안을 물어봐야 하는지 설명합니다. 마지막으로 사용자가 확인하면 Gmail Skill과 Calendar 도구가 실제 행동으로 연결됩니다.”

## 다음 장으로 넘어가는 문장

> “이 구조의 차이는 모두가 가능한 시간이 없을 때 가장 분명하게 드러납니다.”

# 슬라이드 3. 전원 가능 시간이 없어도 조율은 멈추지 않는다

## 이 슬라이드의 역할

핵심 알고리즘, AI를 써야 하는 이유, 안전장치를 한 번에 설명한다. Featy가 단순 캘린더 UI가 아니라는 것을 증명하는 장이다.

## 화면에 넣을 제목

> **전원 가능 시간이 없어도 조율은 멈추지 않습니다**

## 화면에 넣을 4단계 의사결정 흐름

```text
1. 전원 가능 시간 탐색
   전원이 가능하면 바로 1순위 후보 제안

2. 조정 가능 여부 확인
   사용자가 ‘조정 가능’으로 표시한 일정만 대상으로 요청

3. 맥락 기반 대안 생성
   필수 참석자 · 중요도 · 출석률 · 선호 시간 · 비대면 가능성을 반영

4. 사람의 최종 확인
   메일 미리보기 → 초안/발송 → 응답 확인 → 일정 확정
```

## 슬라이드 중앙에 넣을 예시

```text
후보 A  화 14:00  5/5 가능  94점
후보 B  수 16:00  4/5 가능  82점
                     └ 지수: Busy

[조정 요청 메일 만들기]
```

메일 버튼을 누른 뒤의 흐름은 작게 다음처럼 표시한다.

```text
AI가 개인화 문구 생성 → 사용자가 수신자·내용 확인 → Gmail 초안 저장
```

## “AI가 반드시 필요한 이유” 설명

AI를 시간 겹침 계산에 쓰는 것은 설득력이 약하다. 시간 계산은 일반 코드로 충분하기 때문이다. AI가 필요한 지점은 다음 세 가지다.

1. **비정형 요청 해석**  
   “이번 주 오후에, 민재는 꼭 참석하고 가능하면 비대면으로”를 기간·필수 참석자·선호 시간·방식으로 구조화한다.

2. **충돌 상황의 맥락적 중재**  
   단순히 중요도가 낮은 사람을 빼는 대신, 출석 이력·회의 중요도·대체 방식·다음 주 후보를 비교해 타협안을 만든다.

3. **개인화된 커뮤니케이션**  
   같은 충돌이어도 필수 참석자, 선택 참석자, 반복 불참자에게 보내는 요청의 목적과 표현이 달라진다.

## 안전장치

슬라이드 하단에 짧게 표기한다.

```text
일정 내용은 비공개 · 사용자가 표시한 조정 가능 일정만 사용 · 메일/일정 생성 전 최종 확인
```

발표 중 다음을 명확히 말한다.

- AI는 개인 일정을 임의로 이동하지 않는다.
- Busy 상태만 그룹 판단에 사용하며 일정 제목은 공유하지 않는다.
- 이메일은 `dry-run` 또는 Gmail 초안으로 먼저 확인한다.
- 실제 발송과 일정 확정은 사람이 승인한다.

## Value–Term 그래프 배치

오른쪽 하단 또는 배경의 25% 정도에 2×2 포지셔닝 그래프를 넣을 수 있다.

- X축: **단기 빈도** — 일회성 ↔ 반복적
- Y축: **사용자 가치** — 편의 ↔ 의사결정·실행 가치

배치 예시:

```text
높은 가치
  │                       ● Featy
  │           Doodle/When2meet
  │
  │ Google Calendar
  └────────────────────────────
       일회성            반복적
```

Featy가 높은 가치·반복 사용 영역에 있는 이유:

- 팀 회의는 매주 반복된다.
- 후보 탐색뿐 아니라 조정 메일과 확정까지 연결한다.
- 출석 기록이 쌓일수록 추천 품질과 전환 비용이 함께 높아진다.
- 해커톤 팀에서 시작해 스터디·프로젝트·동아리·조직으로 확장할 수 있다.

경쟁 서비스의 세부 기능을 사실처럼 단정하지 말고, 발표에서는 “캘린더 관리/빈 시간 수집/팀 의사결정”이라는 카테고리 차이만 제시한다.

## 발표 대본 예시

> “전원이 가능한 시간이 있으면 계산만으로 충분합니다. Featy의 가치가 생기는 순간은 전원 가능 시간이 없을 때입니다. 먼저 사용자가 조정 가능하다고 표시한 일정이 있는지 확인합니다. 그래도 어렵다면 필수 참석자, 그룹 중요도, 출석 이력, 선호 시간, 비대면 전환 가능성을 함께 보고 대안을 만듭니다. AI는 이 타협의 이유와 개인별 요청 문구를 만들고, 사람은 메일과 일정 생성을 최종 승인합니다. 그래서 자동화는 되지만 통제권은 사용자에게 남습니다.”

## 다음 장으로 넘어가는 문장

> “이 흐름이 실제 화면에서 어떻게 작동하는지 보여드리겠습니다.”

# 슬라이드 4. 계산·설명·행동이 하나의 데모로 이어진다

## 이 슬라이드의 역할

작동 프로토타입, Skill/Plugin 사용, 4명 팀의 구현 근거를 시연과 함께 보여준다. 영상이 있다면 이 슬라이드는 영상 프레임과 세 개의 짧은 증거 문구만 둔다.

## 화면에 넣을 제목

> **계산·설명·행동이 하나의 데모로 이어집니다**

## 화면 구성

### 중앙 70%

웹사이트 시연 영상 또는 라이브 데모 화면을 크게 배치한다. 작은 스크린샷을 여러 개 나열하지 않는다.

### 하단 또는 오른쪽 30%

다음 세 줄만 표시한다.

```text
RULE ENGINE  Top 3 후보와 점수 계산
AI           추천 이유와 충돌 대안 설명
ACTION       확인 후 Gmail 초안·일정 확정
```

### 평가 증거 표기

```text
Skill: gws-gmail-send
Plugin: Caveman — 팀의 AI 커뮤니케이션을 짧고 정확하게 정리
Team: 기획 · 개인 페이지 · 그룹 페이지 · 데이터/통합
```

단, 아래 주의사항을 지킨다.

- `gws-gmail-send`는 저장소에 설치 가이드와 안전한 실행 스크립트가 준비되어 있다.
- Skill 평가를 확실히 받으려면 발표 전 실제 테스트 계정으로 `--draft` 실행 결과를 보여준다.
- 저장소에는 Caveman 플러그인 manifest와 Skill이 존재한다. 그러나 **설치 파일이 있다는 것만으로 실제 활용 증거가 되지는 않는다.** 발표 준비 문구 압축이나 README 정리 과정에서 실제 사용하고, 어떤 결과를 얻었는지 한 문장으로 설명한다.
- Google Calendar/Gmail Plugin을 따로 설치하고 실제로 호출했다면 Caveman 대신 그 플러그인을 전면에 제시하는 편이 제품 흐름과 더 직접적으로 연결된다.

## 권장 데모 시나리오

### 1단계 — 로그인/개인 페이지

보여줄 것:

- Google 로그인 또는 데모 로그인
- 개인 캘린더
- 내가 참여한 그룹 목록

말할 문장:

> “사용자는 자신의 캘린더를 연결하지만, 그룹에는 일정 제목이 아니라 Busy/Free만 공유됩니다.”

### 2단계 — 그룹 페이지

보여줄 것:

- 그룹 멤버 5명
- 개인별 선호 시간과 출석률
- 시간대별 `5/5`, `4/5` 가용성

말할 문장:

> “그룹 페이지에서 캘린더 가용성과 팀의 맥락을 함께 봅니다.”

### 3단계 — 추천 생성

보여줄 것:

- 후보 A: 5/5 가능, 94점
- 후보 B: 4/5 가능, 82점
- AI 추천 이유

말할 문장:

> “후보와 점수는 규칙 엔진이 계산하고, AI는 이미 계산된 결과를 설명합니다.”

### 4단계 — 충돌 중재

보여줄 것:

- Busy 멤버 1명
- `조정 요청 메일 만들기` 버튼
- 개인화된 이메일 미리보기
- 가능하면 Gmail 초안 생성 결과

말할 문장:

> “전원 참석이 어려우면 AI가 조정 대상과 이유를 정리합니다. 실제 전송은 사용자가 수신자와 내용을 확인한 뒤에만 실행됩니다.”

### 5단계 — 일정 확정

보여줄 것:

- 선택 후보 확인 모달
- `Confirm Meeting`
- 확정 완료 상태

말할 문장:

> “최종 결정은 사용자가 내리고, 확정된 결과만 캘린더와 알림으로 연결됩니다.”

## 발표 대본 예시

> “이제 실제 흐름을 보겠습니다. 개인 페이지에서 그룹으로 들어오면 멤버와 전체 가용성을 확인할 수 있습니다. Featy가 후보를 계산하면 화요일 2시는 전원 가능 94점으로 1순위가 됩니다. 전원 가능 시간이 없는 경우에는 Busy인 멤버와 충돌 이유를 표시하고, 조정 요청 메일을 만듭니다. 저희는 `gws-gmail-send` Skill을 연결해 미리보기와 초안 저장을 거친 뒤에만 발송하도록 설계했습니다. 마지막으로 사람이 후보를 확인하면 회의가 확정됩니다.”

## 마지막 10초 마무리

슬라이드를 새로 만들지 않고, 데모 성공 화면 위에서 말한다.

> “오늘 Featy는 다음 회의 시간을 추천합니다. 앞으로는 팀의 반복되는 회의 패턴을 학습해, 충돌을 먼저 발견하고 조율까지 끝내는 팀 스케줄링 에이전트가 되겠습니다.”

# 제품 패러다임 정리

## 한 문장 정의

> **Calendar Management가 아니라 Context-Aware Coordination**

## 기존 방식과 Featy 비교

| 구분 | 기존 캘린더/시간 조사 | Featy |
| --- | --- | --- |
| 입력 | 개인 일정, 선택한 시간 | Busy/Free + 팀 맥락 + 회의 조건 |
| 질문 | 언제 비어 있는가? | 언제 만나야 하는가? |
| 판단 | 사용자가 직접 비교 | 규칙 엔진이 후보와 점수를 계산 |
| AI 역할 | 부가적 | 요청 해석·충돌 중재·이유 설명 |
| 행동 | 일정 표시 또는 투표 | 후보 제안·조정 메일·확정 연결 |
| 통제권 | 사용자 | 사용자 최종 확인 유지 |
| 장기 가치 | 일정 관리 편의 | 반복될수록 팀 패턴과 참석 가능성 개선 |

## 우리 아이디어의 Term / Value

### Term: 반복 사용 가능성

- 팀 회의는 일회성 예약보다 반복 주기가 명확하다.
- 매주 후보 탐색, 불참 조정, 확정 알림이 반복된다.
- 그룹 선호와 출석 데이터가 누적될수록 서비스 재사용 이유가 커진다.

### Value: 해결하는 문제의 크기

- 단순히 시간을 찾는 시간을 줄이는 것에 그치지 않는다.
- 중요한 멤버가 빠지는 회의, 반복 불참, 일정 확정 지연을 줄이는 방향이다.
- 추천에서 끝나지 않고 메일과 캘린더 행동까지 이어져 실행 비용을 낮춘다.

### 발표용 결론

> **높은 반복성 + 높은 실행 가치 영역**에 위치한다.  
> 초기 시장은 해커톤·스터디·프로젝트 팀이고, 장기적으로 반복 회의가 많은 조직의 운영 에이전트로 확장한다.

# AI Agent인가, API 조합인가?

## 발표에서의 답변

> “MVP는 안전한 반자동 에이전트입니다. API가 데이터를 가져오고 행동을 실행하며, AI 에이전트가 여러 도구를 어떤 순서로 사용할지 결정하지만 최종 변경은 사람이 승인합니다.”

## 구조

```text
Google Calendar/API
  └ Busy/Free 데이터 제공

Rule Engine
  └ 후보 생성·점수화

AI Agent
  ├ 자연어 요청 해석
  ├ 후보 이유 설명
  ├ 충돌 대안 선택
  └ 메일 문구 생성

Gmail/Calendar Tool
  └ 승인된 행동 실행
```

## 반드시 에이전트여야 하는가?

- 공통 시간 계산만 한다면 에이전트가 필요 없다.
- 그러나 “조건 해석 → 후보 비교 → 충돌 중재 → 개인별 커뮤니케이션 → 확인 후 실행”처럼 여러 단계와 도구를 오가면 에이전트 구조가 적합하다.
- 해커톤에서는 완전 자율보다 **Human-in-the-loop 에이전트**라고 정의하는 것이 정확하고 안전하다.

# Skill 및 Plugin 설명 자료

## Gmail Skill

### 목적

충돌 멤버에게 개인화된 일정 조정 요청을 Gmail 초안 또는 이메일로 전달한다.

### 적용 흐름

```text
Busy 멤버 탐지
→ AI가 조정 요청 문구 생성
→ 수신자·시간·본문 미리보기
→ gws-gmail-send --draft
→ 사용자 확인 후 필요할 때만 실제 발송
```

### 평가에서 강조할 점

- 단순 설치가 아니라 제품의 핵심 `Action`에 연결된다.
- `--dry-run`, `--draft`를 사용해 안전성과 데모 안정성을 확보한다.
- 실제 발송에는 Calendar 권한과 별도의 Gmail 동의가 필요하다.

## Calendar Skill/API

### 목적

사용자 동의하에 개인 캘린더에서 필요한 Busy/Free 범위를 받아 후보 계산의 입력으로 사용한다.

### 개인정보 원칙

- 다른 멤버에게 일정 제목·설명·장소를 노출하지 않는다.
- 스케줄러에는 시작·종료와 Busy 상태만 전달한다.
- 최종 일정 생성은 사용자가 후보를 확인한 뒤에만 수행한다.

## 현재 저장소의 Plugin

현재 저장소에는 Caveman Plugin manifest와 Skill이 있다. 목적은 AI 커뮤니케이션을 짧고 정확하게 정리하는 것이다.

발표에서 사용 증거를 만들려면 다음 중 하나를 실제로 수행한다.

- 긴 AI 추천 문구를 Caveman Skill로 1~2문장으로 압축해 UI에 반영
- README 또는 데모 안내 문구를 압축한 전후 비교 제시
- 발표자료의 AI 설명을 제한된 UI 공간에 맞게 정리

제품 기능과의 직접성이 약하다고 판단되면, Google Calendar/Gmail Plugin을 설치해 실제 캘린더·메일 흐름에 연결하는 편이 더 강한 증거가 된다.

# 4명 팀 역할을 발표에서 보여주는 방법

# 시연 영상 제작 가이드

## 권장 길이

45~60초. 발표자가 영상을 틀어놓고 90~120초 동안 설명할 수 있도록 핵심 장면만 담는다.

## 촬영 순서

1. 개인 페이지에서 그룹 클릭 — 5초
2. 그룹 멤버와 가용성 확인 — 8초
3. `Find Best Meeting Time` 클릭 — 5초
4. Top 3 후보와 94점 설명 — 10초
5. Busy 멤버의 조정 메일 미리보기/초안 — 12초
6. 후보 선택 및 확정 완료 — 10초

## 촬영 원칙

- 브라우저 확대를 조정해 글자가 발표장에서도 보이게 한다.
- 마우스를 천천히 움직이고 클릭 전 1초 멈춘다.
- 로딩이 긴 부분은 편집하되 결과가 조작된 것처럼 보이지 않게 한다.
- 개인 이메일·토큰·브라우저 알림을 가린다.
- 영상에 배경 음악을 넣기보다 발표자의 설명이 잘 들리게 한다.
- 라이브 데모와 같은 데이터·순서로 녹화해 백업 영상으로 사용할 수 있게 한다.

## 실패 대비

- 인터넷/OAuth 실패: 미리 녹화한 Gmail 초안 생성 영상 사용
- OpenAI API 실패: 저장된 AI 설명을 표시하되, API 호출 코드와 오류 처리 구조 설명
- Calendar 연결 실패: `mvp-demo.json` Busy/Free 데이터를 사용하고 개인정보 경계를 설명
- 화면 전환 실패: 그룹 페이지 직접 URL을 브라우저 즐겨찾기에 준비

# 예상 질문과 답변

## Q1. 그냥 Google Calendar나 Doodle을 쓰면 되지 않나요?

> “기존 도구는 일정 관리나 가능한 시간 수집에 강합니다. Featy는 모두가 가능하지 않은 현실적인 상황에서 필수 참석자, 선호, 출석 이력, 회의 방식을 반영해 타협안을 만들고 실제 조정까지 연결하는 레이어입니다.”

## Q2. AI 없이 알고리즘만 쓰면 되지 않나요?

> “시간 겹침과 점수 계산은 알고리즘이 더 적합합니다. AI는 자연어 조건을 구조화하고, 여러 대안의 의미를 설명하며, 사람별 조정 문구를 만드는 데 사용합니다. 역할을 분리해 안정성과 설명 가능성을 확보했습니다.”

## Q3. 중요도가 낮은 사람을 AI가 임의로 빼는 것 아닌가요?

> “아닙니다. 필수 참석자 여부와 조정 가능 여부는 사용자가 지정합니다. AI는 대안을 제안할 뿐이고, 불참·메일 발송·일정 확정은 사람이 확인합니다.”

## Q4. 개인정보는 어떻게 보호하나요?

> “그룹 판단에는 일정 제목이 아니라 Busy/Free만 사용합니다. OAuth 토큰은 프론트엔드나 Git에 저장하지 않고, 필요한 범위의 권한만 요청합니다.”

## Q5. 실제로 메일을 보낼 수 있나요?

> “`gws-gmail-send` Skill과 데모 스크립트를 연결했습니다. 안전을 위해 기본은 dry-run이고, Gmail 초안으로 확인한 뒤 명시적 승인 시에만 발송합니다.”

## Q6. 3시간 안에 어디까지 만들었나요?

> “로그인/개인/그룹 화면, 후보 점수 계산, AI 설명, 확정 흐름을 P0로 잡았습니다. 실제 OAuth가 불안정할 때는 동일 계약의 mock 데이터를 사용해 핵심 가치가 끊기지 않도록 범위를 관리했습니다.”

## Q7. 장기적으로 수익이나 확장성이 있나요?

> “초기에는 반복 회의를 하는 소규모 팀이 대상입니다. 장기적으로 출석 패턴, 회의 부하, 반복 일정 데이터를 기반으로 조직의 회의 품질과 운영 효율을 개선하는 B2B 에이전트로 확장할 수 있습니다.”

# 발표 전 최종 체크리스트

## 콘텐츠

- [ ] 첫 20초 안에 “빈 시간”과 “최선의 회의”의 차이를 말한다.
- [ ] Goal/Behavior/Context/Action/AI Tool이 하나의 흐름으로 보인다.
- [ ] AI와 Rule Engine의 역할을 명확히 나눈다.
- [ ] AI가 필요한 이유를 시간 계산이 아닌 해석·중재·커뮤니케이션으로 설명한다.
- [ ] Value–Term 그래프에서 Featy의 위치 근거를 말한다.
- [ ] 마지막 문장에서 장기 비전을 회수한다.

## 데모

- [ ] 후보 1은 전원 가능 94점으로 안정적으로 나온다.
- [ ] 후보 2에는 Busy 멤버가 있어 중재 흐름을 보여줄 수 있다.
- [ ] AI 설명 API 실패 시 대체 문구가 있다.
- [ ] Gmail은 발표자 소유 테스트 계정으로 초안 생성이 된다.
- [ ] 실제 메일 발송 버튼은 최종 확인 없이는 실행되지 않는다.
- [ ] 라이브 데모와 동일한 백업 영상을 로컬에 저장했다.

## 평가 증거

- [ ] Skill 실제 실행 화면 또는 로그가 있다.
- [ ] Plugin 실제 사용 전후 결과가 있다.
- [ ] 팀원별 커밋 또는 담당 결과를 보여줄 수 있다.
- [ ] 테스트 결과가 통과한다.
- [ ] API 키·OAuth 토큰·실제 개인 이메일이 노출되지 않는다.
- [ ] 최종 웹사이트 링크 또는 로컬 실행 명령이 준비되어 있다.

# PPT 제작자를 위한 디자인 사양

## 화면 비율과 글자 크기

- 16:9 와이드
- 표지/메인 메시지: 50pt 이상
- 슬라이드 제목: 35pt 이상
- 중간 강조 문구: 24pt 이상
- 본문: 16~20pt
- 한 슬라이드에 긴 문단을 넣지 않는다. 발표 대본은 발표자 노트로 이동한다.

## 추천 색상

현재 Featy 웹 UI와 맞추려면 다음 계열을 사용한다.

- Primary Indigo: `#475DCC`
- Dark Ink: `#1D2938`
- Muted Gray: `#718095`
- Soft Indigo: `#E9EDFF`
- Canvas: `#F6F7FB`
- White: `#FFFFFF`

## 타이포그래피

- 한글: IBM Plex Sans KR 또는 Pretendard
- 영문/숫자: DM Sans
- 제목은 굵고 짧게, 본문은 Regular/Medium을 사용한다.

## 피해야 할 것

- 작은 카드 6~8개를 한 장에 나열
- Behavior/Context/Action을 정의문만으로 채운 표
- 코드 전체나 DB ERD를 발표 슬라이드에 삽입
- 출처 없는 시장 규모·절감 시간·정확도 수치
- “AI가 모든 것을 자동으로 해결한다”는 과장
- 설치만 된 Skill/Plugin을 실제 사용했다고 표현
